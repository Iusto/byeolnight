## 🔧 주요 최적화 사례

### 데이터베이스
- **복합 인덱스**: `(category, created_at)` 등 정렬 순서를 반영해 설계
- **N+1 해결**: 게시판 목록 조회에 Fetch Join 적용

> **⚠️ 채팅 메시지 인덱스 결함 (개선 예정)**
>
> 현재 인덱스는 `(room_id, timestamp)`가 아니라 **`(is_blinded, room_id, timestamp)`** 이다.
> 조회 쿼리(`WHERE room_id = ? AND id < ? ORDER BY timestamp DESC`)에 선행 컬럼인
> `is_blinded` 조건이 없어 **이 인덱스는 range access로 활용되지 않는다.**
> EXPLAIN 검증 없이 인덱스를 추가한 것이 원인이며, `(room_id, id DESC)`로 재설계가 필요하다.
>
> 더불어 **커서 키(`id`)와 정렬 키(`timestamp`)가 달라** 동일 timestamp 구간에서
> 메시지 누락·중복이 발생할 수 있다. 커서를 `id`로 통일해 함께 해결한다.

- **날씨 데이터 캐싱**: 하이브리드 캐싱 전략으로 API 호출 최소화

  - **On-Demand Caching**: 기타 지역은 첫 요청 시 수집 후 캐싱 (WeatherService)

### k6 부하테스트 결과

별도 EC2(t3.micro)에서 k6를 실행하여 캐싱 성능을 검증했다.

#### 테스트 환경
- **부하 생성**: 별도 EC2 t3.micro (애플리케이션 서버와 분리)
- **대상 서버**: 운영 EC2 (Spring Boot + 로컬 캐시)
- **시나리오**: 150 VU, 2분 30초 (ramp-up 30초 → 유지 2분)

> #### ⚠️ 이 측정의 한계 (반드시 함께 읽을 것)
>
> 1. **적중률 100%는 시나리오가 만든 결과다.** 조회 대상이 사전 캐싱된 70개 도시로
>    한정되어 있어 miss가 발생할 수 없다. 이 값은 캐시 성능이 아니라 **상한값**이며,
>    "캐시된 키를 조회하면 캐시에 있다"는 동어반복에 가깝다.
>    의미 있는 측정을 하려면 실제 좌표 분포(로그 기반)나 Zipf 분포로 요청을 생성하고
>    캐시 미등록 지역을 일정 비율 섞어야 한다.
> 2. **부하 생성기가 병목이었을 가능성을 배제하지 못했다.** t3.micro는 vCPU 2개에
>    네트워크 "Low to Moderate" 등급이라, 150 VU에서 생성기 CPU가 먼저 포화되면
>    측정된 지연이 서버가 아닌 생성기의 큐잉 지연일 수 있다. 생성기 측 CPU·소켓 에러를
>    함께 기록하지 않았다.
> 3. **2분 30초는 버스터블 크레딧 구간 안이다.** t3 계열은 baseline 초과분을 CPU 크레딧으로
>    처리하므로, 30분 이상 지속하면 크레딧 소진 후 throttle이 걸린다. 이 결과는
>    **지속 부하(soak) 검증이 아니다.**
> 4. **coordinated omission 보정을 하지 않았다.** 클라이언트 측 지표만으로는
>    응답 지연이 과소평가될 수 있다.
>
> **재측정 시 개선안**: 생성기를 c계열(고정 성능)로 교체 · 양쪽 리소스 동시 모니터링 ·
> 최소 30분 soak · 캐시 미등록 좌표를 포함한 현실적 요청 분포 적용.

#### Weather 캐시 테스트

| 지표 | 결과 |
|------|------|
| 총 요청 | 316,953건 |
| 에러율 | 0% |
| 평균 응답시간 | 20.16ms |

#### ISS 캐시 테스트

| 지표 | 결과 |
|------|------|
| 총 요청 | 290,792건 |
| 에러율 | 0% |
| 평균 응답시간 | 24.05ms |
| p(95) 응답시간 | 51.15ms (**임계값 50ms FAIL**) |
| 초당 처리량 | 1,938 req/s |
| Actuator 검증 | hit 290,778 / miss 14 (한국 영역 1도 그리드 ~25개 키 대상) |

> **p(95) 임계값 초과 원인 및 개선 방향**
>
> - **원인**: 캐시 미스 발생 시 SGP4 궤도 계산(CPU-bound)이 포함되어 응답시간이 증가. miss 14건이 임계값 초과를 유발.
> - **개선 방향 1**: p(95) 임계값을 60ms로 현실적으로 조정 (99.995% 캐시 히트 환경에서 miss 발생 시 계산 시간은 불가피)
> - **개선 방향 2**: SGP4 계산을 `@Async` 비동기 처리로 분리하여 응답 블로킹 최소화
> - **개선 방향 3**: 서버 시작 시 주요 도시 그리드 좌표를 Proactive하게 계산하여 최초 miss 자체를 제거
